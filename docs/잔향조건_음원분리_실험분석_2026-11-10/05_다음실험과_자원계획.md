예상 시간은 현재 Ryzen 5 5600X·GTX 1660 6 GB와 로컬 SSD 사용을 가정한다. 데이터 확보, 설치, 다른 작업과의 자원 경쟁은 별도다. E3의 “새 곡”은 이름만 다른 파일이 아니라 기존 개발·평가 및 확인 가능한 모델 학습곡과 중복되지 않는 녹음을 뜻한다. 그것을 확인하지 못하면 확인 수준을 그대로 보고한다.

E1은 현재 결합 이득이 일반적인 두 모델 결합인지, 추가 잔향에서 특별히 커지는지 구분한다. 개발 세트에서 사후 구성한 분석이므로 탐색적 결과로 표시한다. RIR 유무에 따라 정답도 각각 원 stem·wet stem으로 대응시킨다.

## 2 현재 장비와 역할

| 자원 | 확인값 | 주 용도 |
|---|---|---|
| CPU | AMD Ryzen 5 5600X, 6 cores / 12 threads | 음원 읽기, convolution, STFT, 통계, projection 지표 |

| 연구 환경 | 저장소 `.agent_runtime/banelp-v1/env` | 이미 검증한 라이브러리·모델 사용 |

T1·T2·T5·MWF·MISI는 CPU 실행이 가능하다. CUDA가 필요한 것은 현재 gpuRIR 생성 구현과 GPU 분리기 실행이다. RIR이 이미 생성돼 있으면 후처리 비교 때 매번 GPU로 RIR을 다시 만들 필요가 없다. **CPU에서도 분리 모델을 실행할 수 있는 구현이 있더라도, 현재 CUDA 고정 평가 경로를 임의로 바꾸면 동일 실행 조건이 아니다.**

## 3 실제 측정된 모델 비용

다음 값은 기존 **30초 입력 smoke 측정** 기록이다. 신규 측정이 아니다. RTF는 처리 시간÷입력 오디오 시간이며, 0.5이면 30초 입력의 해당 연산에 15초가 걸린다. warm은 모델을 적재한 뒤의 추론이다. 전체 실험 시간에는 파일 확인·전후처리·지표·집계가 추가된다.

| 모델 | warm RTF | 30초 forward 환산 s | peak allocated MiB | peak reserved MiB |
|---|---:|---:|---:|---:|
| HTDemucs | 0.063 | 1.89 | 623 | 872 |
| BS-RoFormer ep17 | 0.851 | 25.53 | 2,970 | 4,224 |
| SCNet small | 0.163 | 4.89 | 2,552 | 2,886 |
| SCNet large Starrytong | 0.698 | 20.94 | 2,454 | 4,064 |
| SCNet large 9.3244 | 0.694 | 20.82 | 2,454 | 4,064 |
| SCNet XL ep54 | 0.909 | 27.27 | 2,568 | 4,226 |

allocated는 텐서 등에 실제 할당된 메모리이고 reserved는 allocator가 확보한 영역이다. 두 값을 더하지 않는다. 디스플레이·다른 프로세스·드라이버 메모리는 별도다. 표가 허용 최대 사용량을 보장하지 않는다.

두 모델을 순서대로 실행하면 현재 평균 방법의 warm forward RTF 예상은 `0.063+0.851=0.914`다. 개발 40개 조건의 순수 forward는 약 18.3분, 평가 160개 조건은 약 73.1분이다. **실제 평가 단계는 약 91.8분**이었으므로 73.1분을 end-to-end 실행시간으로 쓰지 않는다.

SCNet small 평균의 같은 계산은 RTF 약 0.226이다. 이는 속도 검토의 근거일 뿐 해당 방법이 기존 평가 40곡에서 같은 품질을 냈다는 뜻은 아니다.

## 4 실제 완료된 실행 시간

11월 10일 재개 실행은 앞선 cache를 재사용했다. 따라서 아래 합계는 맨 처음부터 모든 모델을 계산한 시간이 아니다.

| 단계 | 실제 경과 시간 | 주요 연산 |
|---|---:|---|
| 완료된 5개 모델 dev cache 확인 | 약 52초 | 파일·cache 확인 |
| SCNet XL 남은 dev 29조건 | 14분 2초 | GPU 추론 |
| 개발 후보 전체 비교 | 53분 38초 | CPU 후처리·지표, donor GPU 추론 |
| 정답 magnitude/phase 등 진단 | 30분 12초 | CPU STFT·projection 지표 |
| 누출 점검·후보 고정 | 약 1초 | 메타데이터 검증 |
| 선택 후보 평가 40곡 | 91분 46초 | GPU 분리, CPU 지표 |
| 평가 bass 투영 진단 | 1분 25초 | CPU |
| 재개 실행 전체 | **약 3시간 12분** | 18:23:48~21:35:45 KST |

실제 로그의 초 단위 값은 `실측_단계별시간.csv`에 있다. 앞선 5개 모델 계산·설치·다운로드·장애 중단 시간은 이 합계에 포함하지 않는다.

기존 30초 개발 표본 한 개에서 후처리만 잰 시간은 T1 0.29초, T2 α=2 4.98초, T5 4.76초, MWF 0회 4.02초, MWF 2회 23.20초, C2 2회 25.63초였다. 곡당 비용의 편차와 지표 계산을 제외한 단일 표본 측정이므로 전체 실험 ETA에는 여유를 둔다.

## 5 새 실행 시간을 산정하는 방법

`총시간 = 모델 적재 + Σ(입력 초 × 모델별 RTF) + 후처리 + 지표 + 파일 I/O`

E1은 10곡×30초=300초 입력이다. 두 모델의 warm forward 예상은 약 4.6분이며, 지표와 확인을 더해 실행 20~40분을 배정했다. E3의 예시 48조건은 1,440초이므로 warm forward 약 21.9분, 전체는 1~2시간으로 잡았다. 둘 다 **가정에 따른 예산이며 실제 측정값이 아니다.**

CPU 전용 모델 추론은 현 장비에서 측정하지 않았다. GPU 시간에 임의 배수를 곱해 시간을 제시하지 않는다. GPU를 쓸 수 없다면 30초 개발 입력 3개를 먼저 실행해 모델 적재와 warm 시간을 분리해서 측정한다.

학습 시간은 `sec/step × 총 step`으로 계산한다. 예를 들어 측정 후 0.5초/step, 20,000 step이 확정되면 순수 학습 계산은 약 2.8시간이다. 이는 계산 예시이며 현재 보정망의 성능·속도 예측이 아니다. 검증·저장·데이터 생성 시간을 별도로 더한다.

## 6 청취 평가 설정 제안

처음에는 10~12명의 **예비 평가**를 계획한다. 통계 검정력을 보장하는 표본 수로 제시하지 않는다. 예비 분산과 피로도를 보고 본 평가 규모를 정한다.

각 참가자에게 12개의 A/B trial을 제시한다. 일반 사례 8개와 사전에 선택한 실패 사례 4개를 구분하고, 각 trial은 특정 stem의 같은 10~15초 구간을 비교한다. vocals·drums·bass·other가 균형 있게 포함되도록 배정한다. 기준/결합의 순서와 표시를 무작위화한다.

질문은 다른 악기 누출, 목표 음원 손실, 인공적인 거친 소리, 전체 선호도를 구분한다. 정답 stem을 들을 수 있는 연습을 마련한다. 음질 선호 평가에서는 재생 loudness를 맞춘 사본을 쓰되, 원래 출력의 이득·손실 검토는 같은 재생 gain의 별도 비교로 남긴다. **개별 loudness 정규화가 bass의 이득 손실을 가릴 수 있기 때문이다.**

정답 오디오·출력 길이·정렬을 먼저 확인한다. 최악 사례만 들어 전체 선호도로 일반화하지 않는다. 음악의 파일·모델 이용 조건에 따라 팀 내부 비교 자료로 관리한다.
